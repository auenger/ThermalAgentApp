# Icepak 动态 Python 与可复用仿真能力计划

记录日期：2026-10-20  
目标分支：`feat/plugin-adaptive-repair`  
状态：推进中。代码与替身测试进展见 [实现记录](DYNAMIC_ICEPAK_IMPLEMENTATION.md)，真实 Windows/Icepak 验收尚未完成。

## 计划摘要

交付目标：让安装后的 App 在具备 Icepak 环境的机器上，根据实际仿真需求动态生成和加载 Python；运行成功的方法沉淀为可复用的本地脚本，再通过不同参数驱动有界仿真迭代，减少因新增操作或环境兼容小问题而重复打包。

- **操作可扩展**：支持实际工程需要的操作，不局限于 fan 通道参数。
- **能力可积累**：保存脚本、参数定义、适用环境和运行证据，App 重启后继续调用。
- **迭代可追溯**：记录每轮参数、求解结果、最佳方案与停止原因。
- **交付可验证**：提供 Windows 安装包和手动验收说明，以真实环境中的运行结果确认完成程度。

本文记录目标和实施计划，不将规划项视为已完成功能。代码进度见实现记录，实机验收步骤见 [Windows 验收说明](DYNAMIC_ICEPAK_WINDOWS_ACCEPTANCE.md)。

## 1. 已确认的目标

这个分支的主要目的，是把适合插件化的仿真能力尽量交给插件处理。App 提供稳定的执行底座，AI 根据用户需求与实际 Icepak 工程动态编写、加载和执行 Python，使仿真操作不再局限于已经写好的 fan 通道参数接口。

动态 Python 的首要用途是扩展仿真操作能力；环境兼容修复是支撑能力。对于材料、热源、边界条件、网格、求解设置等受 Icepak/PyAEDT 接口支持的操作，不应每新增一种操作就修改宿主并重新打包。

脚本在有环境的机器上执行并验证成功后，进入 App 管理的本地脚本库。后续相同或兼容需求优先复用，避免每次重新生成。这里的“内置”是指登记为 App 可调用的本机能力，而不是重新编译进安装包。

在此基础上，App 能根据仿真结果调整参数，在明确的目标、参数范围和运行预算内自动迭代。达到目标、耗尽预算或出现无法处理的问题时停止，并保留过程与结果。不能预先承诺所有仿真问题都能收敛。

## 2. 目标流程

1. 用户描述仿真目标、可调整参数及约束。
2. App 读取当前工程、对象标识、已有设置及本机运行环境。
3. 查找适用的本地脚本；存在匹配能力时优先复用。
4. 缺少能力时，AI 根据实际工程与可用接口生成 Python。
5. 在测试工程副本上执行，获取日志、错误、变更读回和输出产物。
6. 对失败进行分类：脚本或接口问题可在预算内修正；许可证、环境缺失或需求不明确等问题给出明确状态。
7. 经验证成功的操作提取为带参数的脚本，连同适用条件和验证证据登记到本地脚本库。
8. 后续任务复用脚本完成参数调整、求解与结果提取，并按目标继续迭代。

必须分别记录“脚本执行成功”“修改结果读回一致”“求解完成”和“目标达成”。前一项不能代替后一项。

## 3. 立项时的基础与差距

根据本轮已核对的分支记录，已有插件版本管理、依赖环境、兼容选择、验证记录、回退机制，以及限定故障投递 DSH 和修复候选存档能力。部分 AEDT 标准安装路径问题已有自动适配机制。

立项时已有的修复候选是故障修复入口，不能直接视为面向仿真操作的动态脚本执行入口。以下是本计划需要补齐并验收的主线，最新进度以实现记录及第 8 节验收清单为准：

- 面向 fan 参数接口之外需求的动态 Python 执行。
- 动态操作的工程读回与真实求解验证。
- 成功脚本的参数化、登记、检索和跨会话复用。
- 根据仿真结果持续调整参数的有界迭代流程。
- 对现有功能进行全面插件化盘点与迁移。

后续实施需要先核对最新源码，不以本文替代代码审计。

## 4. 架构分工

| 层次 | 职责 |
| --- | --- |
| App / Core | 用户目标、工程与任务管理、执行调度、策略、过程展示和记录 |
| Icepak 执行插件 | 连接 AEDT、读取工程、运行动态脚本、传递参数、取消任务、返回日志与结果 |
| 动态 Python 脚本 | 表达具体仿真操作，提供前置检查、参数修改和结果读回逻辑 |
| 本地脚本库 | 管理脚本版本、参数定义、适用条件、验证证据和调用记录 |
| AI / DSH | 查找与选择脚本、生成缺失操作、分析失败、提出后续参数调整 |

宿主保留稳定且通用的执行协议，具体工程操作优先放入插件或脚本。安装包包含必要的执行桥接和基础脚本，无需预先打包所有未来的 Python 操作代码；宿主协议或内置运行时本身变更仍可能需要发新版。

## 5. 实施阶段

### 第一阶段：盘点能力并定义执行协议

- 梳理现有 fan 参数修改、工程读取、求解及结果提取流程，识别可复用部分与宿主中的硬编码。
- 定义动态脚本的输入、输出、执行状态、错误分类和取消机制。
- 明确工程副本、AEDT 会话和任务的归属，防止并行操作同一工程造成冲突。
- 确定脚本引用及内容摘要、环境身份、参数快照、工程标识和产物记录方式。

交付：能力盘点、执行协议，以及一个不依赖固定 fan 参数接口的最小执行入口。

### 第二阶段：完成一个真实动态操作闭环

- 在有 Icepak 的机器上选定一个现有 fan 通道参数接口之外的场景，例如修改测试对象的热源功率；具体场景以测试工程具备的对象为准。
- AI 基于真实对象与接口生成脚本，由 App 通过执行插件运行。
- 在工程副本上检查修改前后值、保存并重新读取工程确认结果。
- 沿用求解操作的现有授权策略，执行求解并提取结果。
- 记录失败原因，允许在明确预算内修正脚本并重新验证。

验收：从自然语言需求到真实操作、读回、求解和结果展示，全程不修改宿主代码、不重新打包 App。

### 第三阶段：成功脚本沉淀与复用

- 将成功操作提取为显式参数，去除写死的本机路径、工程名和对象名。
- 为脚本保存用途、参数类型与单位、取值约束、对象匹配条件、环境要求和验证级别。
- 根据内容摘要管理版本，并记录来源、验证工程特征、运行结果和变更历史。
- 相似需求优先检索本地脚本，执行前重新检查适用条件。
- 脚本更新保留旧版本；失败脚本不能覆盖已有可用版本。
- App 重启后仍可查找和调用已登记脚本。

验收：第二次提出同类需求时，可传入不同参数调用已有脚本；不重新生成代码，仍能读回并确认结果。

### 第四阶段：有界仿真参数迭代

- 明确目标指标、允许修改的参数、参数范围及停止条件。
- 组织“调整参数 → 求解 → 提取指标 → 判断目标 → 下一轮”的任务流程。
- 分开处理执行失败与指标未达标，避免把求解失败当成可比较的结果。
- 保留每轮参数、脚本版本、工程副本、结果和耗时，记录当前最佳可行方案。
- 支持用户取消；达到目标、轮数或耗时上限后停止并说明原因。

验收：在选定测试案例中完成多轮实际运行，展示参数与指标变化；达到约定目标或按停止条件正确退出，不虚报收敛。

### 第五阶段：扩大插件化覆盖

- 按需求逐步覆盖材料、热源、边界条件、网格、求解设置和结果后处理。
- 对可参数化操作沉淀脚本；需要稳定领域接口的能力封装成插件。
- 根据实际 Windows、AEDT 和 PyAEDT 组合积累兼容证据，不默认跨版本适用。
- 将共性的环境检查和兼容处理纳入执行前检查，减少重复故障。

跨机器共享、远程脚本市场和批量分发不作为第一轮必需项；先完成本机生成、验证、复用。

## 6. 建议的脚本登记信息

以下为目标数据设计，不作为现有接口的完整说明；具体字段以实现记录与代码为准。

| 信息 | 内容 |
| --- | --- |
| 身份 | 脚本 ID、版本、内容摘要、创建时间、来源 |
| 用途 | 操作描述、适用场景、检索标签 |
| 输入 | 参数类型、单位、默认值、范围、对象选择条件 |
| 前置条件 | 工程状态、对象类型、必要属性、环境与依赖要求 |
| 执行约定 | 入口、超时、取消方式、重复执行语义、变更范围 |
| 输出 | 结构化状态、变更读回、指标、日志与产物位置 |
| 验证记录 | 测试环境、工程特征、参数、验证级别、结果和时间 |
| 生命周期 | 草稿、已验证可复用、停用；历史版本与失败记录 |

“已验证可复用”应附带验证范围。例如只验证了参数写入的脚本，不应标记为已经通过真实求解。需要不同验证要求的调用方必须检查这些记录。

## 7. 执行要求

- 对工程的探索性修改首先在副本中执行，保留原始工程。
- 不把模型文字或进程退出码单独当作工程验证通过；以结构化结果、工程读回及对应求解产物确认。
- 不同工程复用前检查对象和参数适用性，不默认对象名称一致。
- 沿用现有求解确认策略，避免新增每步重复确认；用户明确授权的自动迭代范围以任务参数和预算记录。
- 明确超时、取消、子进程清理及工程占用处理，避免遗留任务持续消耗资源。
- 输入数据错误、代码错误、环境问题、许可证问题及求解失败分别呈现。
- 动态加载和运行模型代码的执行边界需要独立设计，不能把工具调用白名单等同于 Python 运行边界。
